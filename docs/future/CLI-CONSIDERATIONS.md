# CLI Considerations

**Status**: Research & Design (March 2026)
**Context**: Should Syto ship a CLI version of its transformation engine?

---

## The Strategic Question

Before building a CLI, we asked: what's our moat compared to `duckdb -c "SELECT ..."` or a Python script? SQL is universal, every LLM knows it, and DuckDB handles gigabytes. Python/pandas has infinite flexibility. Why would anyone use a `syto` CLI?

### What a Syto CLI Is Not

A Syto CLI is **not** a general-purpose data query tool. It cannot and should not compete with:

- **DuckDB/SQL** on ad-hoc queries, dataset size, or expressiveness
- **Python/pandas** on flexibility, ecosystem, or programmability
- **csvkit/Miller** on Unix-style composability for quick shell tasks
- **jq** on focused, single-format transformation

Attempting to compete on any of these axes would be a losing proposition.

### What a Syto CLI Actually Is

The CLI's value is **executing workflows that were built visually** (or generated by an LLM agent that can produce inspectable artifacts):

```
Build visually (browser)  -->  workflow.json  -->  Run headlessly (CLI)
         ^                                                |
         |                                                v
         +---- Human inspects/tweaks <---- results -------+
```

The **transparency loop** is the moat, not the CLI itself:

- Human builds workflow visually in Syto's browser UI
- Exports `workflow.json`
- Runs it headlessly in CI/cron/scripts via CLI
- Can re-open in browser to inspect, debug, or modify

For LLM agents specifically:

- Agent generates `workflow.json` (a declarative, inspectable artifact)
- Runs it via CLI
- Human can open the same file in Syto's browser UI to understand what the agent did
- This is fundamentally different from an agent writing opaque Python scripts

**The spec format is the moat. The CLI is just a runner for that spec.**

## Competitive Landscape Analysis

### Projects That Attempted "Visual Builder -> Portable Spec -> CLI"

| Project               | Architecture                                            | Spec Format                     | Adoption            | Outcome                                                                     |
| --------------------- | ------------------------------------------------------- | ------------------------------- | ------------------- | --------------------------------------------------------------------------- |
| **OpenRefine**        | Java GUI, JSON operation history, headless via HTTP API | JSON array of operations        | ~11k stars          | CLI requires spinning up full Java server. Not truly standalone.            |
| **KNIME**             | Java GUI + batch executor                               | XML directory structure         | Strong (enterprise) | Spec is GUI serialization, not human-readable or hand-editable.             |
| **Pentaho Kettle**    | Spoon (GUI) + Pan/Kitchen (CLI)                         | XML files                       | Strong (enterprise) | Proved the pattern works. But heavyweight Java, verbose XML.                |
| **Weaverbird**        | Vue builder -> JSON steps -> Python backends            | JSON pipeline (clean, readable) | 108 stars (7 years) | Architecturally closest to Syto. Barely adopted outside its parent company. |
| **AWS DataBrew**      | AWS console -> JSON recipes -> AWS execution            | JSON array of actions           | Moderate            | Clean spec format but locked to AWS ecosystem.                              |
| **Trifacta/Wrangler** | Stanford research -> commercial DSL                     | Proprietary "Wrangle" language  | Acquired by Alteryx | Started as academic breakthrough. Became proprietary enterprise tool.       |

### Projects That Succeeded as CLIs (Different Pattern)

| Project    | Pattern                        | Why It Worked                                                |
| ---------- | ------------------------------ | ------------------------------------------------------------ |
| **dbt**    | SQL + YAML files, CLI executor | Met users where they were (SQL). Massive VC backing.         |
| **jq**     | DSL string IS the spec         | Hyper-focused on one format (JSON). Zero deps. Frictionless. |
| **csvkit** | Unix tools composed via pipes  | Followed Unix philosophy. No new spec to learn.              |
| **Miller** | CLI verb chaining with `then`  | Combined power with Unix composability.                      |

### Key Finding

Three patterns work at scale:

1. **Focused CLI, no visual builder** (jq, csvkit, Miller) -- Unix philosophy wins
2. **Code-first, visualization derived** (dbt) -- use languages people already know
3. **Heavy enterprise GUI + bolted-on CLI** (KNIME, Pentaho, Alteryx) -- captive audiences

The pattern that has NOT proven itself at scale:

- **"Clean JSON spec as primary artifact with both visual and headless consumers"** -- architecturally the cleanest, adoption-weakest (Weaverbird: 108 stars in 7 years)

### Why Weaverbird's Low Adoption Doesn't Necessarily Doom Us

See [WEAVERBIRD-COMPARISON.md](../WEAVERBIRD-COMPARISON.md) for full analysis. Key differences:

1. Weaverbird was built for ToucanToco's commercial product, not as a standalone tool
2. Weaverbird requires a server to execute anything -- you can't just use it
3. Syto's browser-first approach means the visual builder works with zero infrastructure
4. The CLI would share 100% of code with the browser engine (no dual-language tax)

## Design Decisions

### Decision 1: Radically Minimal MVP

**Chosen approach**:

```bash
syto run workflow.json < data.csv > result.csv
syto validate workflow.json
syto schema data.csv
```

**Rejected alternatives**:

**a) Full CLI toolkit with single-transform mode**

```bash
# Rejected: ad-hoc transform piping
cat data.csv | syto apply filter --expr "age > 30" | syto apply select --columns name,email
```

Why rejected: This competes directly with DuckDB/csvkit/Miller on their home turf. Those tools are better at ad-hoc CLI queries. Syto's strength is the visual builder + portable spec, not typing transforms in a terminal.

**b) Interactive REPL mode**

```bash
syto interactive data.csv
> filter age > 30
> select name, email
> export result.csv
```

Why rejected: Same problem -- competing with DuckDB's interactive mode, which is superior. Also adds significant implementation complexity for marginal value.

**c) Extensive introspection commands**

```bash
syto transforms list
syto transforms describe filter
syto functions list
syto functions describe trim
```

Why rejected for v1: These are useful for LLM agents, but the same information is better served as documentation/JSON files shipped with the package. An agent can read `syto-transforms.json` once rather than calling CLI commands repeatedly. Could be added later if demand materializes.

### Decision 2: CSV Piping via stdin/stdout

**Chosen approach**: Standard Unix I/O conventions.

```bash
syto run workflow.json < data.csv > result.csv
syto run workflow.json --input data.csv --output result.csv  # explicit form
cat data.csv | syto run workflow.json | other-tool            # composable
```

Why: Follows Unix conventions. Works naturally with pipes. Both humans and LLM agents understand stdin/stdout.

### Decision 3: Workflow from File or stdin

**Chosen approach**: Accept workflow JSON from a file path argument. Consider also accepting from stdin with a flag.

```bash
syto run workflow.json < data.csv          # workflow from file, data from stdin
syto run --workflow - --input data.csv     # workflow from stdin, data from file
```

Why: Agents may want to generate workflow JSON on the fly and pipe it directly rather than writing to a temp file. Supporting both is low-cost and high-value.

### Decision 4: --json Flag for Structured Output

**Chosen approach**: Default output is CSV (for piping). `--json` flag outputs JSON data rows.

```bash
syto run workflow.json < data.csv                # CSV output (for piping/humans)
syto run workflow.json --json < data.csv         # JSON output (for agents)
syto schema data.csv                              # Pretty table (for humans)
syto schema data.csv --json                       # JSON schema (for agents)
syto validate workflow.json                       # Human-readable validation
syto validate workflow.json --json                # Structured validation result
```

Metadata (schema, row counts, etc.) is NOT mixed into `--json` output. If needed later, a separate `--meta` or `--verbose` flag could add it. Principle: `--json` means "output the data as JSON," not "output everything as JSON."

### Decision 5: Package Strategy

**Options considered**:

**a) Separate npm package (`@syto/cli`)**

- Pro: Clean separation, independent versioning
- Con: Must keep core in sync, publish complexity, import paths

**b) `bin` field in current package**

- Pro: Simplest approach, shared code directly
- Con: Installs browser dependencies (Preact, etc.) unnecessarily for CLI users

**c) Monorepo with shared core (npm workspaces)**

- Pro: Clean package boundaries, shared code via workspace references
- Con: Migration effort to restructure existing code

**Decision**: TBD. Leaning toward (b) for MVP simplicity -- the extra dependencies are a minor annoyance, not a blocker. Can migrate to (c) later if the CLI gains traction.

### Decision 6: Binary Name

`syto` -- matches the project name. Need to verify npm availability before publishing.

## Core Engine Portability Assessment

The `src/core/` directory was architecturally designed for portability from the start (see SPECIFICATION.md and SOUL.md). Assessment:

### Ready (Zero Changes Needed)

- All 20+ transform handlers -- no browser APIs
- Expression engine (parser, validator, interpreter) -- pure logic
- Schema engine (type inference, propagation) -- pure logic
- Type converter, error formatter -- pure logic
- EDA engine -- pure logic
- All functions (date, math, string, regex, json, type) -- pure logic
- `src/i18n/core.ts` -- portable i18next registry, no browser APIs

### Must Exclude from CLI Bundle

Both modules moved out of `src/core/` on 2026-09-21, so the exclusion is now structural rather than
a bundler setting:

- `src/app/services/charts.ts` -- imports `vega-embed` (DOM rendering)
- `src/app/services/expression-language.ts` -- imports `@codemirror/*` (editor support)

### Dependencies

Required for CLI: `arquero`, `jsep`, `i18next`, `papaparse` -- all Node-compatible.
Not needed: `vega-embed`, `@codemirror/*`, `preact`.

### Test Validation

All core tests run via Vitest in Node.js. No browser polyfills needed. This confirms portability.

## What the CLI Needs to Implement

### Phase 1: MVP

1. **CLI entry point** (`src/cli.ts` or similar) -- ~100-200 lines
   - Argument parsing (minimal -- could use `commander` or `yargs`, or even manual parsing for zero deps)
   - Read CSV from file or stdin (PapaParse)
   - Read workflow JSON from file
   - Initialize i18n
   - Apply transforms sequentially via `applyTransform()`
   - Write result CSV to stdout or file

2. **Validate command** -- check workflow JSON against transform schemas without executing

3. **Schema command** -- infer and display column types from a CSV file

4. **Structured errors** with meaningful exit codes:
   - 0: success
   - 1: invalid arguments / bad input
   - 2: workflow validation error
   - 3: transform execution error

### Future Phases (Only If Demand Exists)

- `syto transforms list/describe` -- introspection for agents
- DuckDB backend translator (same workflow JSON, different executor)
- Batch mode (process multiple files)
- Progress indicators for large datasets
- Performance metrics

## Multi-Backend Future

Weaverbird's architecture validates that the same pipeline spec can be executed by completely different engines (they proved it with Pandas, MongoDB, and 6 SQL dialects).

Syto's workflow JSON could follow the same path:

```
workflow.json  -->  Arquero executor (browser + Node.js CLI)    [today]
                -->  DuckDB translator (large datasets, SQL)    [future]
                -->  Polars/Arrow translator (performance)      [future]
```

The CLI should be designed with this in mind -- the executor should be a pluggable interface, even if there's only one implementation initially. This means:

- The CLI entry point should not hardcode Arquero calls
- Transform execution should go through a clean interface
- Adding a new backend should only require implementing that interface

This is validated by both Weaverbird's architecture and SOUL.md's stated vision: "The transformation JSON format should become stable enough to be a portable specification that could be executed by different backends."

## Open Questions

1. **npm name availability** -- is `syto` taken? Need to check before committing to the name.
2. **Packaging** -- separate package vs. bin field vs. monorepo. MVP can use bin field; revisit later.
3. **Multi-file workflows** -- how does the CLI handle joins that reference other datasets? Probably `--input` accepts multiple files with names: `--input main=data.csv --input lookup=regions.csv`.
4. **Workflow format stability** -- the CLI creates a versioning contract. Need to ensure `FUTURE-PROOFING.md` constraints are sufficient.
5. **Node.js version requirements** -- what's the minimum Node.js version? Affects distribution strategy.
